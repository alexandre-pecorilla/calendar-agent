# R1 — Correctness review (2026-10-09)

Independent, read-only review of the build as of 2026-10-09 18:25 (105 hermetic tests green, `tsc --noEmit` clean). Scope: `src/availability`, `src/calcom`, `src/llm`, `src/pipeline`, `src/config`, `src/security`, the unit/integration tests and fixtures, against CLAUDE.md, the scope (§3, §5, §6, §7) and `docs/architecture/{availability,llm,pipeline}.md`. Every finding below was reproduced with a script run against the real modules (section "Experiments run"); nothing is inferred from reading alone.

## Summary

The interval arithmetic, schedule evaluation (overrides, `24:00`, split hours, days without rules), cross-zone clipping, DST days in both directions, the open-range computation, the listing cap and empty-day rule, the Cal.com client (query format checked against the Cal.com API v2 reference) and the DeepSeek cost math (checked against the published pricing page) are sound. The defects are concentrated in three places: the point-verdict logic around "now" and durations, the reply verifier, and whole-day detection when the asker is not in the owner's zone. Verdict: not ready to accept as is; the two high findings produce wrong yes/no answers or let a wrong phrasing through, and each has a small, local fix.

Findings: **2 high, 4 medium, 5 low**. No critical finding: nothing leaks calendar content, nothing can write to Cal.com, no exception escapes the pipeline.

## Findings

### R1-1 [high] A point question at "now" (or within the next five minutes) is answered "busy" although the owner is free

**Where:** `src/availability/windows.ts:88-111` (`classifyPoint`) together with `freeWindows` (`windows.ts:30-31`, clip at `roundUpToMinutes(now, 5)`), called from `src/availability/engine.ts:119-128`.

**What:** `classifyPoint` first rejects `point < now` as past, then looks the point up in `freeWindows(...)`, which clips every window to `now` rounded **up** to the next 5 minutes. Any point in `[now, ceil5(now))` is therefore inside no free window and falls through to the `busy` branch, with "next free window" starting a couple of minutes later. The past check is also exact to the millisecond, so "at 10:00" asked at 10:00:30 is "already in the past". The user guide invites exactly these questions ("free Monday at 4?", "now").

**Reproduction** (schedule 09:00–18:00, no busy block, `now` = Tue 2026-10-13 10:03 New York):

```
point 10:03  -> busy | No, Owner is busy Tuesday Oct 13 at 10:03 AM. Next free window: 10:05 AM to 6:00 PM, New York time.
point 10:04  -> busy | No, Owner is busy Tuesday Oct 13 at 10:04 AM. Next free window: 10:05 AM to 6:00 PM, New York time.
point 10:05  -> free | Yes, Owner is free Tuesday Oct 13 from 10:05 AM to 6:00 PM, New York time.
point 10:00 asked at 10:00:30 -> past
```

Expected: "Yes, Owner is free Tuesday Oct 13 from 10:05 AM to 6:00 PM" (or from 10:03) for the first two; a point a few seconds old should not be "in the past".

**Proposed fix:** in `classifyPoint`, (1) compute the lookup windows without the "now" clip (`now: i.dayStart`), since futureness is already checked; when the point is inside a free window, report the window from `max(point, ceil5(now))` to the window end; (2) make the past test minute-based (`i.point < i.now.startOf('minute')`) or snap a point in `[now, ceil5(now))` to `ceil5(now)` in `AnswerPipeline.buildRequest`. Add unit cases for point = now, now+1 min, now−30 s.

### R1-2 [high] The verifier accepts phrased replies that change the date, swap or convert times, invert the verdict, or add a bullet line

**Where:** `src/llm/verify.ts:8-9` (token regexes) and `:23-38` (`verifyReply`); `src/availability/render.ts:22` collects date tokens that are never checked.

**What:** Verification is a set-membership test on time tokens matching only `h[:mm] AM|PM` and `Hh[mm]`, plus "every draft bullet line appears somewhere" and "required phrases present". Consequently: date tokens are never extracted from the reply; `HH:MM` (24-hour), `16 h 30` (French typography with spaces), "midnight"/"noon" are invisible; the order of tokens is not checked, so "from 5:30 PM to 4:00 PM" or a "Yes"→"No" rewrite passes; bullet lines may be reordered or supplemented with an invented line built from allowed tokens. `docs/architecture/availability.md` ("Rendering") states the phrasing is accepted only if it uses no time **or date** token the renderer did not produce, and README says "verified token by token"; the implementation is weaker than documented. The model runs at temperature 0 with a strict prompt, so drift is rare, but the verifier is the only guard between call 2 and Slack (CLAUDE.md §2), and when it misses, the user receives a confidently wrong answer.

**Reproduction** (draft: `Yes, Owner is free Monday Oct 12 from 4:00 PM to 5:30 PM, New York time.`, tokens `Monday Oct 12, 4:00 PM, 5:30 PM`, required `New York time`). All of the following return `{ok: true}`:

```
Yes, Owner is free Tuesday Oct 13 from 4:00 PM to 5:30 PM, New York time.          (date changed)
Yes, Owner is free Monday Oct 12 from 5:30 PM to 4:00 PM, New York time.           (times swapped)
No, Owner is busy Monday Oct 12 at 4:00 PM. Next free window: 5:30 PM, New York time.   (verdict inverted)
Yes, Owner is free Monday Oct 12 from 15:00 to 17:30, New York time.               (24h times, 15:00 is wrong, invisible)
Yes, Owner is free Monday Oct 12 from 4:00 PM until midnight, New York time.
Oui, Owner est disponible lundi 12 octobre de 16 h 00 à 17 h 30, heure de New York time.  ("16 h 00" invisible)
```

Listing draft with bullets Mon Oct 12 / Tue Oct 13: a reply with the two lines reordered **plus** `• Wed Oct 14: 9:00 AM to 5:00 PM` (built from allowed tokens) also passes. `extractTimeTokens('16 h 30 and 16h and 4.30 PM')` → `["30:00 PM","4:00 PM","16h00"]` shows the gaps.

**Proposed fix:** (1) extract date tokens with regexes mirroring `formatDate`/`formatDateLong` (EN `\b(Mon|Tue|…|Monday|…) (Jan|…) \d{1,2}\b`, FR `\b(lundi|…) \d{1,2}(er)? (janvier|…)\b`, case-insensitive) and require membership in `tokens`; (2) widen the time regexes to `\b\d{1,2}\s?[:h]\s?\d{2}\b`, `\b\d{1,2}\s?h\b` and `\b\d{1,2}(:\d{2})?\s?(am|pm)\b` with whitespace normalised, so a 24-hour or spaced time can only pass if it is in `tokens`; (3) require the ordered sequence of extracted time tokens in the reply to equal the draft's sequence (this covers swaps and verdict rewrites for point replies at no extra cost); (4) require the count of lines starting with `•` to equal the draft's and their order to be monotonic. Update `llm.md` to describe exactly what is checked. Add the six replies above as negative tests.

### R1-3 [medium] "All day" is never rendered when the asker's zone differs from the owner's schedule zone

**Where:** `src/availability/windows.ts:114-119` (`isWholeDayFree` uses luxon `DateTime.equals`, which also compares zone and locale) and `src/availability/engine.ts:161,173` (`dayWorking` is built from `dayWorkingIntervals`, i.e. in the schedule zone, while the windows carry the display zone).

**What:** For every asker whose Slack zone is not the owner's, a fully free day is listed as a plain window ("3:00 PM to 12:00 AM") instead of "all day, 3:00 PM to 12:00 AM" promised by scope §5.3 and both user guides. The unit test for whole days uses the same zone on both sides, so it cannot see this.

**Reproduction** (owner schedule America/New_York 09:00–18:00, no busy block, Tuesday 2026-10-13):

```
display America/New_York | wholeDay = [ true ]  | • all day, 9:00 AM to 6:00 PM
display Europe/Paris     | wholeDay = [ false ] | • 3:00 PM to 12:00 AM
display Europe/Brussels  | wholeDay = [ false ] | • 3:00 PM to 12:00 AM
isWholeDayFree(same instants, different zone objects) = false
```

**Proposed fix:** compare instants, not DateTime objects: `w[0].start.toMillis() === k[0].start.toMillis()` (same for `end`); additionally `.setZone(zone)` the `dayWorking` intervals at `engine.ts:161` as is already done for `working` at `:132`. Add a unit case with asker zone ≠ schedule zone.

### R1-4 [medium] A point question with a duration says "busy" and "no other availability" when the owner is free but the window is shorter than the duration

**Where:** `src/availability/windows.ts:103-106` (free-but-too-short collapses into `{kind: 'busy'}`), `src/availability/render.ts:118-131` (busy wording; the duration is neither mentioned nor added to `required`).

**What:** "Do you have an hour Monday at 4:30?" with the owner free 4:30–5:00 PM produces a factually false statement ("is busy … at 4:30 PM") and, when no later window of an hour exists, "No other availability that day", although the day still has availability. Scope §5.1 asks the duration to be stated in the first line; for point questions it never is, so the asker cannot tell the answer was filtered by duration.

**Reproduction** (schedule 09:00–17:00, no busy block, point Tue 2026-10-13 16:30, duration 60):

```
busy | No, Owner is busy Tuesday Oct 13 at 4:30 PM. No other availability that day, New York time. | required = ["New York time"]
```

**Proposed fix:** add a verdict `{kind: 'free_short', window, next}` and render it as "Owner is free Tuesday Oct 13 at 4:30 PM but only until 5:00 PM; next window of at least 1 hour: …" (FR: "… mais seulement jusqu'à 17h00 ; prochain créneau d'au moins 1 h : …"), and push the formatted duration into `required` for every point reply that carries one. Keep "No other availability that day" only when `durationMin` is unset.

### R1-5 [medium] `buildRequest` trusts the model's `intent: "day"` over the dates, so a multi-day range renders as one mislabelled day

**Where:** `src/pipeline/answer.ts:261` (`kind = p.intent === 'day' || … <= 1 ? 'day' : 'range'`); `src/availability/render.ts:157-166` (a `day` result prints the header from `res.rangeStart` and the windows of the first day that has any).

**What:** The parse prompt tells the model to set `range_start = range_end` for a day, but nothing in code enforces it. If call 1 returns `intent: "day"` with a three-day range, the engine computes three days and the renderer prints the first date in the header with the first non-empty day's windows under it.

**Reproduction** (request `{kind: 'day', rangeStart: Mon 2026-10-12, rangeEnd: Thu 2026-10-15}`, Monday fully busy 09:00–18:00):

```
days computed = [ '2026-10-12:0', '2026-10-13:1', '2026-10-14:1' ]
Owner's availability Monday Oct 12, New York time:
• all day, 9:00 AM to 6:00 PM          <- these are Tuesday's windows; Monday is fully booked
```

**Proposed fix:** derive the kind from the dates only: `const kind = endExclusive.diff(start, 'days').days <= 1 ? 'day' : 'range'`; in `renderResult`, for `kind === 'day'` assert `res.days.length <= 1` (or render `res.days[0]`). Add a pipeline test with `intent: 'day'` and a multi-day range.

### R1-6 [medium] Timezone override: abbreviations are accepted with the wrong offset, and an unusable override silently moves the asked time to another zone

**Where:** `src/availability/timezone.ts:5-7` (`isValidZone` = luxon `IANAZone.isValidZone`, which accepts legacy names) and `:29-37` (`resolveZone` falls back silently); `src/pipeline/answer.ts:159,243`.

**What:** Two related behaviours. (a) "4 pm EST" makes the model emit `EST`, which luxon accepts as a fixed UTC−5 zone with no DST: in summer the computed instant is one hour off from Eastern time, and the label becomes "EST time" / "heure d'EST". `CET`, `US/Eastern`, `PST8PDT`, `utc` are accepted likewise. (b) When the model emits something unusable ("Paris", "Eastern Time"), `resolveZone` falls back to the asker's zone and `point_time`, which the prompt told the model to express in the override zone, is re-interpreted in the asker's zone: a confident answer about the wrong instant, with the asker's label.

**Reproduction** (asker America/New_York, question meaning "9 am Paris time" on 2026-07-13, model `point_time` = 09:00):

```
override 'Paris'        -> zone America/New_York (asker)    instant 2026-07-13T13:00Z   label "New York time"   (should be 07:00Z)
override 'EST'          -> zone EST (override)              instant 2026-07-13T14:00Z   label "EST time"        (Eastern time would be 13:00Z)
override 'CET'          -> zone CET (override)              instant 2026-07-13T07:00Z   label "CET time"
override 'Eastern Time' -> zone America/New_York (asker)    label "New York time"
zone 'utc'              -> label "utc time" / "heure d'utc"
```

**Proposed fix:** accept an override only if it is `UTC` or canonical `Area/City` (contains `/` and is not `Etc/…`, `US/…`); map common abbreviations before validation (EST/EDT→America/New_York, CST/CDT→America/Chicago, MST/MDT→America/Denver, PST/PDT→America/Los_Angeles, CET/CEST→Europe/Paris, GMT/BST→Europe/London, IST→Asia/Kolkata, JST→Asia/Tokyo); when `timezone_override` is non-null and still unusable, return the `clarify` reply instead of falling back. Tell the prompt to emit `Area/City` only.

### R1-7 [low] One unexpected element empties the whole `excluded_weekdays` list; `part_of_day` and `point_time` are dropped on harmless variants

**Where:** `src/llm/parse.ts:16-20`.

**What:** `z.array(z.enum(...)).catch([])` discards the entire list when any element is not an exact lowercase name, and nothing downstream notices (the weekday is then not in `required` either, so the verifier cannot catch it). `part_of_day: "Morning"` becomes `null` (whole day listed), `point_time` with seconds or a trailing `Z` becomes `null` (clarification).

**Reproduction:** `excluded_weekdays: ['Wednesday']` → `[]`; `['monday','Weds']` → `[]`; `part_of_day: 'Morning'` → `null`; `point_time: '2026-10-12T16:00:00'` → `null`; `'2026-10-12T16:00Z'` → `null`.

**Proposed fix:** normalise before validating: `z.array(z.string()).transform(a => a.map(s => s.trim().toLowerCase()).filter(isWeekdayName))`, lowercase `part_of_day`, accept `T\d{2}:\d{2}(:\d{2})?` and strip a trailing `Z`/offset (or treat an explicit offset as an override). Reject the question (clarify) rather than silently widening it when a weekday name is unrecognised.

### R1-8 [low] "Afternoon" stops at 18:00, contrary to scope §5.5, and this is not documented for users

**Where:** `src/availability/engine.ts:63-67` (`partOfDaySpan`), `src/llm/prompts/parse.md:30`.

**What:** The scope defines afternoon as "12:00 onward"; the build defines afternoon 12:00–18:00 and adds "evening" 18:00–24:00. For an owner whose hours run past 18:00 (the live schedule is 07:00–19:00), "Tuesday afternoon?" hides 18:00–19:00. Neither user guide mentions the cut-off.

**Proposed fix:** either make afternoon 12:00→end of day (evening may overlap it), or keep the split and document it in both user guides and `availability.md`.

### R1-9 [low] Label and date cosmetics in French and for unusual zones

**Where:** `src/availability/timezone.ts:10-24`, `src/availability/format.ts:11-20`.

**What:** h-aspiré cities are elided ("heure d'Hong Kong", "heure d'Havana", "heure d'Ho Chi Minh"); city names are not translated ("heure de London"); the first of the month renders "jeudi 1 octobre" instead of "1er octobre"; `Etc/GMT+2` renders "GMT+2 time" although that zone is UTC−2 (POSIX sign); `US/Eastern` → "Eastern time". Multi-segment zones (`America/Argentina/Buenos_Aires` → "Buenos Aires"), underscores, `Asia/Kolkata`, midnight/noon ("12:00 AM"/"12:00 PM", "0h00"), single-digit hours ("9h05") are all correct.

**Proposed fix:** a small exception set for h-aspiré and a translation map for the ~20 most common cities; `d` → `d'er'` when `t.day === 1` in French; render `Etc/GMT±n` as `UTC∓n`.

### R1-10 [low] `Collector.range` formats the raw instants but collects tokens in the display zone (latent)

**Where:** `src/availability/render.ts:40-44` (`range` calls `this.time(a)` with `setZone` for the token set, then `formatRange(a, b, lang)` without it).

**What:** Every current caller passes display-zone instants, so the text and the token set agree today; a future caller passing a schedule-zone or UTC instant would produce text that its own verifier rejects (or, worse, text in one zone with the label of another). Reproduced: `formatRange` on Paris instants with display zone New York → "9:00 AM to 10:00 AM" while the tokens hold "3:00 AM"/"4:00 AM".

**Proposed fix:** `return formatRange(a.setZone(this.zone), b.setZone(this.zone), this.lang)`.

### R1-11 [low] Limits: `checkLimits` runs twice per question; refused and failed questions count toward the budget; the budget day is UTC

**Where:** `src/pipeline/answer.ts:138-139`, `src/pipeline/rate-limit.ts:17-22`, `src/db/repos/queries.ts:108-131`.

**What:** The verdict is computed twice (six `COUNT(*)` queries instead of three). Rows for `rate_limited`, `over_capacity` and `cannot_check` outcomes are inserted with a Slack entry point, so they consume the daily budget and the per-minute windows although they cost no model call; `daily_budget` resets at 00:00 UTC, which `pipeline.md` does not state. None of this changes an availability answer.

**Proposed fix:** compute the verdict once; exclude `intent IN ('rate_limited','over_capacity')` (and optionally `error IS NOT NULL`) from `countSince` for the budget; document the UTC day.

## What was checked and found sound

- `mergeIntervals` / `subtractIntervals` / `clipIntervals`: overlapping, nested, touching and zero-length intervals; busy ending exactly at "now"; busy touching the window edges; 24-hour busy block; empty day.
- Noise floor (15 min) and duration filter: applied after merge, `max(noise, duration)`; 10-minute gap dropped, 15-minute gap kept.
- Schedule evaluation: weekday rules, days without rules, date overrides replacing the day, an all-day-unavailable override (`00:00`–`00:00` → day dropped), `24:00` end, split hours, schedule zone ≠ display zone (Paris 20:00–24:00 seen from New York as 2:00–6:00 PM).
- DST: Europe/Paris 2026-10-25 (01:00–05:00 → 300 real minutes) and 2026-03-29 (→ 180 minutes, the missing hour), America/New_York 2026-11-01 (busy across the repeated hour → 90 + 210 minutes) and 2026-03-08, plus cross-zone days (NY display of a Paris schedule on Oct 25 → 4:00 AM–12:00 PM; Paris display of a NY schedule on Nov 1 → 3:00–11:00 PM) and the morning split on a 25-hour day (780 minutes). All correct.
- Windows crossing display-zone midnight are split and grouped per day; year boundary and leap day format correctly; Feb 30, Feb 29 2027 and `T25:00` are rejected (clarification).
- Week start: luxon `Info.weekdays` is Monday-first in both `en-US` and `fr-FR`, matching `weekdayNumber` and `DateTime.weekday`; exclusions therefore map correctly.
- Open range: next 5 days with hours; after hours on Friday → Mon–Fri next week (today hidden, 8-day range); at 17:00 Friday → Friday's remaining hour listed first.
- Listing cap (10 days with availability, "first days shown") and the empty-day rule (≤ 7-day ranges only); "no availability" header when nothing is free.
- Horizon and past handling in `buildRequest`: `today + 28 + 1` exclusive, ranges clipped, start clipped to today, inverted or missing dates → clarify, past → fixed reply; point beyond horizon → fixed.
- Cal.com client: `GET` only, frozen allowlist, both `cal-api-version` values, retries on network/429/5xx with backoff, 401/403 → `unauthorized`, non-JSON → `bad_response`, `source` stripped at parse time. Query format `timeZone`, `dateFrom`, `dateTo`, repeated `calendar=<credentialId>,<externalId>` confirmed against the Cal.com API v2 reference (the documentation MCP server `cal-com`, "GET /v2/calendars/busy-times": `loggedInUsersTz` deprecated in favour of `timeZone`; "only the first comma separates the two values, so an externalId containing commas is kept intact"). Date widening (−1/+1 day in the schedule zone) covers the observed clipping at `dateTo`.
- Schedule schema matches `GetDefaultScheduleOutput_2024_06_11` (`days`, `startTime`/`endTime` HH:MM, `overrides[{date,startTime,endTime}]`, `isDefault`); `overrides` defaulted to `[]`.
- DeepSeek cost: prices and the peak windows ("01:00–04:00 and 06:00–10:00 UTC, Monday through Friday, excluding Chinese public holidays") match the pricing page fetched 2026-10-09; `isPeak` uses UTC; cache-hit tokens priced separately; reasoning tokens counted as output.
- Fixed replies: all 11 kinds × 2 languages, elision ("d'Hélène", "de Marie"), horizon weeks derived from the setting.
- Language fallback: parsed `en`/`fr` wins, Slack locale is the tiebreaker, English otherwise; fixed replies issued before parsing use the locale.
- Error containment: every Cal.com/DeepSeek failure inside `ask` maps to `cannot_check` with an error code; `phraseReply` catches its own errors and returns the draft; the Slack handlers catch anything thrown by the pipeline; the sandbox validates the zone and "pretend now" before calling the pipeline. No unhandled promise found in `app.ts` listeners (all awaited).
- Sanitiser: mentions, channel and link markup removed, entities decoded, 500-character cap, control tokens neutralised, empty → help without any provider call.
