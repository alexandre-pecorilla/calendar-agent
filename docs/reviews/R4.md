## Summary

**Verdict: safe to keep running; distributable to colleagues after the one high finding (and ideally the two mediums) is fixed, which action plan §10 requires before tagging `v1.0.0`.** Every hard limit of the scope holds in code and under test: free/busy only (`source` stripped at parse time, no event object exists anywhere), read only (one `GET`, frozen allowlist, 100-question path-set test), the model has no tools and sees nothing worth leaking, the asker's text reaches only the parse call and its output is schema-bound, the phrase call's output is verified against the deterministic draft, secrets are envelope-encrypted with AAD and never rendered or logged, the container is hardened as documented and published only on loopback and the Tailscale IP, and the live injection corpus (30/30 in-process, 12/12 through the container's sandbox) produced only fixed replies or plain availability answers with nothing leaked. The weaknesses found are about the admin's availability on the private network and about a log-level foot-gun, not about calendar content, keys or Cal.com writes.

Counts: **0 critical, 1 high, 2 medium, 6 low.**

## Findings

### R4-1 [high] The admin login lockout is global, so anyone who can reach the admin port can keep the owner locked out
- Where: `src/admin/auth.ts:164-167`, `src/db/repos/sessions.ts:369-371`, `src/admin/routes/login.ts:90-100`, schema `src/db/migrations/0001_init.sql:174-178`.
- Issue: the lockout counts every failed login in the last 15 minutes with no client dimension:
  ```ts
  export function lockoutRemainingSeconds(sessions: SessionsRepository, now: Date): number {
    const since = new Date(now.getTime() - LOCKOUT_WINDOW_MINUTES * 60_000).toISOString();
    return sessions.failedLoginsSince(since) >= LOCKOUT_THRESHOLD ? LOCKOUT_WINDOW_MINUTES * 60 : 0;
  }
  ```
  `login_attempts` has the columns `id, at, success` only (observed on the scratch database). Five wrong passwords from any client, with any `X-Forwarded-For`, lock `/login` for everyone, including the owner with the right password (`locks out after five failures` in `tests/integration/admin.test.ts` shows exactly this). Attempts made during a lockout are not recorded, so the lock lasts 15 minutes from the fifth failure; a client that repeats five failures each time the window reopens keeps the owner out indefinitely. The per-IP limiter does not help because its key is attacker-chosen (R4-2), and the lock is checked before the scrypt work, so the loop costs the attacker nothing.
- Exploit scenario: any device on the tailnet (a colleague's laptop on a shared tailnet, a compromised phone, anything that reaches `http://<tailscale-ip>:8400` or the HTTPS Serve address) runs a few `curl` lines in a loop; the owner cannot open the admin (query log, settings, workspaces, sandbox) until the loop stops. Slack answering is unaffected. Precondition: reaching the admin port, which the threat model restricts to the tailnet.
- Fix (code + docs): replace the hard 15-minute global lock with a progressive delay per failure (for example `min(2^(n-1), 60)` seconds before the next attempt is accepted, computed from the last failure time), which keeps brute force at a handful of scrypt verifications per minute without ever refusing the right password for more than a minute; or keep a global lock only as a high ceiling (for example 100 failures) and make the five-failure lock per client key. Update `docs/architecture/security.md` ("five failures lock it for 15 minutes") and `docs/architecture/admin.md` accordingly, and name the residual.

### R4-2 [medium] `trustProxy: true` lets every client choose the IP the rate limiter keys on and the login log records
- Where: `src/admin/server.ts:37` (`Fastify({ logger: false, trustProxy: true, bodyLimit: 64 * 1024 })`), `src/admin/routes/login.ts:88` (`rateLimit: { max: 20, timeWindow: '1 minute' }`), `:92, :99, :106` (`{ ip: req.ip }`), `node_modules/@fastify/rate-limit/index.js:58` (`defaultKeyGenerator = (req, ipv6Subnet) => normalizeIP(req.ip, …)`).
- Issue: with `trustProxy: true` Fastify takes `req.ip`, `req.hostname` and `req.protocol` from `X-Forwarded-For`, `X-Forwarded-Host` and `X-Forwarded-Proto` whatever the socket's remote address. Tailscale Serve is the only legitimate proxy, but direct tailnet clients on port 8400 reach the same listener, and inside the container every host-published connection arrives from the Docker bridge anyway, so the header is trusted from everyone. Observed on the scratch instance: a failed login sent with `X-Forwarded-For: 203.0.113.9` was logged as `{"level":40,"ip":"203.0.113.9","msg":"admin login failed"}`; the same request without the header as `"ip":"127.0.0.1"`.
- Exploit scenario: a tailnet client rotates the header to make the 20-per-minute limiter see a new client on every request (the lockout still caps real guessing at five per 15 minutes, which is why this is medium, not high), and to attribute its attempts to any address it likes in the operator's logs, which is the only forensic trace the admin keeps.
- Fix (code + docs): log both `req.socket.remoteAddress` and the forwarded value under distinct keys (`socketIp`, `forwardedFor`) so the log is honest about provenance; stop keying the login limiter on `req.ip` (fold it into the R4-1 progressive delay, which needs no client key), or key it on the socket address; keep `trustProxy` only for the `Secure` cookie and the installer's origin check, which cannot be abused by the sender; correct `docs/architecture/admin.md` ("20 per minute per IP").

### R4-3 [medium] `LOG_LEVEL=debug` writes full Slack event payloads, question text included, to the container logs
- Where: `src/slack/app.ts:9-22` (`boltLogger`: `debug: (...m) => log.debug({ bolt: m.map(String).join(' ') })`), `src/logging/logger.ts:144-166` (redaction by key only; `bolt` not listed and a substring cannot be), `node_modules/@slack/bolt/dist/App.js:400` (`this.logger.debug(JSON.stringify(body))`), `node_modules/@slack/socket-mode/dist/src/SocketModeClient.js:315` (`Received a message on the WebSocket: ${payload}`) and `:340` (ack data), `.env.example:63-64` (`# fatal|error|warn|info|debug|trace`), `docs/architecture/configuration.md` (`LOG_LEVEL` row), `Makefile:67` (`logs: ## … never contain question or answer text`).
- Issue: the wrapper forwards Bolt's `debug` calls to pino under the `bolt` key; pino filters by `LOG_LEVEL`. At `info` nothing content-bearing is emitted (verified on the live logs and by the canary test). At `debug`, Bolt logs every event body and the socket-mode client logs every raw frame. Demonstrated with the built code: `boltLogger(createLogger('debug')).debug(JSON.stringify(body))` printed `{"level":20,…,"bolt":"{\"event\":{…\"user\":\"U0CANARY\",\"team\":\"T0CANARY\",\"text\":\"is the owner free Monday? CANARY-QUESTION-TEXT\"}}"}`; at `info` it printed nothing. `debug` and `trace` are advertised as ordinary values with no warning, and the control-11 statement, the `make logs` help and `DEPLOYMENT.md` §6 are unconditional.
- Exploit scenario: an operator (the owner or a colleague running their own instance) sets `LOG_LEVEL=debug` to investigate a Slack problem; from then on every question, asker id and team id lands in the Docker json-file logs on the host (rotated, but up to 50 MB kept), outside the SQLite file that is supposed to be the only place content lives, and outside the backup discipline. Precondition: the operator changes a documented variable.
- Fix (code + docs): cap the Bolt and installer loggers at `INFO` regardless of `LOG_LEVEL` (make the wrapper's `debug` a no-op, or pass `LogLevel.INFO` and ignore `setLevel`), so content never reaches pino from the Slack libraries; alternatively document that `debug`/`trace` log full Slack payloads and must not be used on an instance that answers real people. Add a test that drives `boltLogger` at `debug` with a payload containing a marker and asserts the marker is absent.

### R4-4 [low] The reply verifier does not refuse Slack broadcast and mention markup, `mailto:`/bare-domain links, or a reply about someone other than the owner
- Where: `src/llm/verify.ts:132` (`if (/https?:\/\/|www\./i.test(text)) return { ok: false, reason: 'link' };`), `src/llm/prompts/phrase.md:9` (third person about the owner is a prompt rule only).
- Issue: with a `yes` draft, `verifyReply` accepted `<!channel> Yes, Alex is free Monday Oct 12 from 4:00 PM to 5:30 PM, New York time.`, `Yes, Marie is free Monday Oct 12 …` and `… See example.com or mailto:x@y.z` (all `{"ok":true}` on the built code). Slack renders `<!channel>`/`<!here>`/`<!everyone>` in `chat.postMessage` text as a channel-wide notification and `<@U…>` as a mention. Call 2 never sees the asker's text, so only a model hallucination can produce these, which is why this is low; the verifier exists precisely to make hallucinations harmless.
- Exploit scenario: none driven by a user; a spontaneous `<!here>` in a thread reply would notify a whole channel on the bot's behalf.
- Fix (code): extend the link check to `/<[!@#]|mailto:|\b[a-z0-9-]+\.(com|net|org|io|fr|example)\b/i` (or simply refuse any `<` in the reply, since the draft never contains one), and push `ownerName` into `required` in `renderResult` so a reply that drops or swaps the name falls back to the draft.

### R4-5 [low] An out-of-range `page` parameter makes `/queries` answer 500
- Where: `src/admin/routes/queries.ts:13` (`const pageNo = Math.max(1, Number(q.page ?? '1') || 1);`), `src/db/repos/queries.ts:102-106` (`LIMIT ? OFFSET ?` bound with `(pageNo - 1) * PAGE_SIZE`).
- Issue: `page=1e30` or `page=99999999999999999999` gives an offset that is not a safe integer; `node:sqlite` raises `datatype mismatch` and the error handler returns 500 (`{"error":"internal"}`; the log line holds the message and the path only, no content). Observed on the scratch instance; `page=-5` and `page=abc` are fine.
- Exploit scenario: authenticated owner only; a bookmarked or mistyped URL. No leak, no persistence; a nuisance.
- Fix (code): clamp with `Number.isSafeInteger` and an upper bound (for example `Math.min(pageNo, 1_000_000)`), and reuse the clamp for `offset` in the repository.

### R4-6 [low] The repository guards are regex tripwires that a lowercase or concatenated spelling walks past
- Where: `tests/repo/calcom-allowlist.test.ts:18-20` (the method regex accepts only an upper-case `[A-Z]+` value after `method:`, and the write-verb regex only the quoted upper-case words `POST`, `PUT`, `PATCH`, `DELETE`), `:25` (the path regex extracts a quote-delimited `/v2/…` made of `[a-zA-Z0-9/_-]` only), `:32-33` (counts `fetchImpl(` in `client.ts` only); `tests/repo/no-llm-tools.test.ts:16` (the regex `\btools\s*:|\bfunctions\s*:|tool_choice|function_call|parallel_tool_calls` over `src/llm` and `src/pipeline` only), `:21-23`.
- Issue: checked on the built Node: `new Request(url, { method: 'post' }).method === 'POST'` (Fetch normalises the six standard verbs), and the guard regexes report `method: 'post'`, `method: ['PO','ST'].join('')` and `method: verb` as not caught; `'/v2/calendars/../bookings'` and `'/v2/bookings?x=1'` yield no path at all, so the allowlist comparison never runs on them; a `fetch(` or `new Request(` in any other file under `src/` is not counted. The runtime check `ALLOWED_SET.has(path)` in `CalcomClient.get` and the single-fetch structure are the real control; the guards only need to be honest about what they catch.
- Exploit scenario: a future contributor (or a sloppy AI session) adds a write path and the gate stays green. No runtime exposure today.
- Fix (tests): make the method regex case-insensitive and fail on any `method:` whose value is not the literal `'GET'`; fail on any `fetch(` / `new Request(` / `http.request(` under `src/` outside `src/calcom/client.ts` (the OpenAI SDK's own fetch lives in `node_modules`); check every string containing `/v2/` rather than only quote-delimited clean paths; extend `no-llm-tools` to all of `src/` and to the bracket spellings (`['tools']`, `"tools"`, `tools=`).

### R4-7 [low] Backups are written world-readable
- Where: `Makefile:83-90` (`db-backup`: `$(COMPOSE) cp app:/data/backups/$$name backups/$$name`), observed `-rw-r--r-- 644` on the file `make db-backup` created (deleted afterwards) and on the pre-existing `backups/calendar-agent-20261009-173033.db`.
- Issue: the snapshot holds the query log in clear (who asked what, answers, display names) by design D9; the secrets in it are ciphertext. `.env` is kept at 600 but the backup that reveals the same audit trail to any local user is 644.
- Exploit scenario: another account on the host (or a sync tool that mirrors the directory) reads the questions. Precondition: a shared host or an unattended copy.
- Fix (config): `chmod 600 backups/$$name` in the target (and `umask 077` before the `cp`), state the mode in `docs/architecture/data.md` "Backups".

### R4-8 [low] Sessions outlive a password change and have no idle timeout or cap
- Where: `src/db/repos/sessions.ts:312` (`SESSION_TTL_DAYS = 30`), `:329-338` (`create`), `:340-351` (`find` refreshes `last_seen_at` but never uses it), `src/admin/routes/login.ts:102-105` (every successful login creates a new row; nothing bounds the count), `src/index.ts:43` (boot purges expired rows only).
- Issue: a session is valid for 30 days from creation whatever happens: editing `ADMIN_PASSWORD` in `.env` and `make restart` does not invalidate cookies issued under the old password, so the documented response to a suspected password leak (change it) does not end an attacker's session. The hermetic suite created a cookie for each login with no cap, as the scratch instance did.
- Exploit scenario: a cookie copied from an unlocked browser stays valid up to 30 days even after the owner rotates the password.
- Fix (code + docs): store a non-secret fingerprint of the current password (for example the first 8 bytes of an HMAC under `MASTER_KEY`) in `settings` and, at boot, `deleteAll()` sessions when it changes; add an idle timeout (for example 7 days from `last_seen_at`) and a "log out everywhere" button; document that rotating the password ends sessions.

### R4-9 [low] Hardening opportunities: no HSTS on the HTTPS origin, unauthenticated `/health` details, base image by floating tag, fixed master-key id
- Where: `src/admin/headers.ts:171-178` (no `Strict-Transport-Security`; observed absent on `https://…:8445/login` too, Tailscale Serve does not add one); `src/admin/server.ts:54-62` (`/health` returns `botName`, `installMode`, `slackConnected`, `workspaces` to anyone who reaches the port; observed `{"botName":"alex-calendar-agent","installMode":"multi","slackConnected":true,"workspaces":1}` on the live instance); `Dockerfile:6` (`FROM node:24-alpine`, not digest-pinned); `src/crypto/envelope.ts:41` (`parseMasterKey(encoded, id = 'k1')`: every key is `k1`, so the `madeWithKeyIds` warning in `src/index.ts:48` can never name a different id and tamper/rotation are told apart by the GCM tag alone).
- Issue: each is a documented or accepted trade-off; none crosses a boundary. HSTS only matters for the Serve address; `/health` discloses the owner's first name through the bot name on a private network; the floating tag means `make rebuild` can pull a different base; the key id is cosmetic.
- Fix (config/docs): add `Strict-Transport-Security: max-age=31536000` when `req.protocol === 'https'`; trim `/health` to `{ok, slackConnected}` for unauthenticated callers (the Makefile `status` target only needs those); pin `node:24-alpine@sha256:…` and bump it deliberately; derive the key id from a short hash of the key, or drop the id from the warning.

## What was checked and found sound

- User text reaches only call 1: `src/pipeline/answer.ts:148` passes `sanitized.text` to `parseQuestion`; `:197` passes `{ ownerName, lang, draft }` to `phraseReply`; `grep` confirms no other reference to `sanitized.text` or `rawText` after line 148.
- Nothing the model returns is used unvalidated: `parsedQuestionSchema` (`src/llm/parse.ts:183-193`) with `.catch(null)` per field; `normalizeZoneOverride` (`src/availability/timezone.ts:27-36`) accepts only `UTC`, mapped abbreviations or `Area/City` names that `IANAZone.isValidZone` knows, refusing `Etc/`, `US/` and bare cities; dates re-parsed by luxon and clipped to today/horizon in `buildRequest`.
