# R2 — Integration review (2026-10-09)

Independent round, no prior context. Scope: boot and failure modes, Socket Mode, both install
modes, the admin end to end, sandbox parity, Docker/Compose/Makefile, `.env` handling, database
operations, and installability from `DEPLOYMENT.md`. Availability maths were out of scope (R1).
Method: code reading of `src/slack`, `src/admin`, `src/index.ts`, `src/config`, `src/db`,
`src/services` and the relevant `node_modules` internals (`@slack/oauth`, `@slack/socket-mode`,
`@slack/bolt`); hermetic checks on the repository; a scratch copy under the session scratchpad
driven with `curl` (single and multi mode, Slack off, fake keys); read-only inspection of the live
container plus one `docker compose restart app`. No repository file other than this report was
touched (`git status --porcelain` empty before writing it); `.env` was never read.

## Summary

Verdict: **ship after fixing R2-1 and the three medium items that affect the documented install
path (R2-2, R2-4, R2-5)**. The runtime is solid: every boot failure is contained or fails closed
with the right exit code, SIGTERM is handled, the socket reconnects in under two seconds after a
restart, the admin resists everything I threw at it, the container hardening in the compose file
is what Docker actually applied, and all hermetic gates pass (lint, typecheck, 114 tests,
docs-check, secrets scan). The defects are at the seams: the multi-workspace installer only works
when the admin is opened at `PUBLIC_BASE_URL` (the OAuth state cookie is `Secure` and host-bound,
the "Add to Slack" link is relative), `.env` is parsed four different ways (inline comments after an
empty value become the value inside the container), `make manifest` cannot run at the step the
guide puts it, the install-failure page can never show the codes the troubleshooting table names,
and the status flag never drops when the socket is lost.

Counts: 0 critical, 1 high, 5 medium, 7 low.

## Findings

### R2-1 [high] Multi-mode install fails with `invalid_state` unless the admin is opened at `PUBLIC_BASE_URL`

**Where:** `src/slack/install-routes.ts:34-37` (install path served on whatever origin the admin
is open on), `src/admin/routes/workspaces.ts:19` (relative link `href="/slack/install"`),
`node_modules/@slack/oauth/dist/install-provider.js:645-648` (state cookie
`slack-app-oauth-state=…; Secure; HttpOnly; Path=/; Max-Age=600`, no `Domain`),
`DEPLOYMENT.md` §4–5 ("Open `http://127.0.0.1:<port>` (or the Tailscale address)… admin →
Workspaces → Add to Slack").

**What:** `@slack/oauth` binds the OAuth state to the browser with a cookie that is (a) flagged
`Secure`, so a browser discards it when the admin is open over plain `http://` on anything but
localhost (`http://100.64.0.1:8400`, `http://myhost:8400`), and (b) host-only, so even on
localhost it is never sent to `https://<host>.<tailnet>.ts.net:8445/slack/oauth_redirect`. The
callback then fails with `slack_oauth_invalid_state` on every attempt, and the failure page points
the operator at the wrong cause ("loaded twice on a phone"). The only working path is to open the
admin at the HTTPS `PUBLIC_BASE_URL` first; neither the Workspaces page nor `DEPLOYMENT.md` says
so. The T6 evidence recorded only the 302 from the HTTPS origin; no install was completed.

**Reproduction (scratch instance, multi mode, Slack off):**
```
GET /slack/install  (session cookie, plain http, Host: evil.example)  → 302
  Set-Cookie: slack-app-oauth-state=<…>; Secure; HttpOnly; Path=/; Max-Age=600
  Location: https://slack.com/oauth/v2/authorize?…&redirect_uri=https%3A%2F%2Fr2.example.ts.net%3A8445%2Fslack%2Foauth_redirect
GET /slack/oauth_redirect?code=fakecode&state=<same state>   (no cookie, as a browser on another host would send)
  → 400 "Slack reported slack_oauth_invalid_state"
```
(The `redirect_uri` is correctly built from `PUBLIC_BASE_URL`, not from the request host.)

**Proposed fix:** render the Workspaces link as the absolute
`${PUBLIC_BASE_URL}/slack/install`; in the `/slack/install` handler, when `req.protocol !==
'https'` or `req.hostname` differs from the `PUBLIC_BASE_URL` host, redirect to that absolute URL
before calling `handleInstallPath`; state in `DEPLOYMENT.md` §4 that the install must start from the
HTTPS address; add a line to the failure page for `slack_oauth_invalid_state` ("start from
`<PUBLIC_BASE_URL>/workspaces`"). Then complete one real install as evidence.

### R2-2 [medium] `.env` is parsed four different ways; inline comments in the template change values inside the container

**Where:** `.env.example` (inline `# …` comments on `SLACK_SIGNING_SECRET=`, `ADMIN_PASSWORD=`,
`MASTER_KEY=`, `CALCOM_API_KEY=`, `DEEPSEEK_API_KEY=`, `LOG_LEVEL=`, `COMPOSE_PROJECT_NAME=`,
`SLACK_APP_TOKEN=`, `SLACK_BOT_TOKEN=`); `docker-compose.yml:13` (`env_file: .env`);
`Makefile:8` (`grep … | cut -d= -f2-`), `Makefile:92` (`make status`); `scripts/check-ports.mjs:20-21`;
`Makefile:138` (`make test-live` sources the file with the shell).

**What:** Node's `--env-file` (used by `make ask`, `make manifest`, `make *-check`) strips inline
comments and yields `""` for an empty value. Docker Compose strips the comment after a non-empty
value but keeps it when the value is empty, so a line left as in the template reaches the container
as the comment text. The Makefile and `check-ports.mjs` keep the comment entirely. Consequences:
a `SLACK_SIGNING_SECRET=` left empty passes validation only inside the container (value
`# Basic Information → App Credentials`); an `ADMIN_PASSWORD=` left empty is refused on the host but
becomes the literal password `# long; the admin login` in the container; an inline comment a user
adds after `APP_BIND_ADDRESSES` makes `make up` add `compose.publish-2.yml` with `APP_PUBLISH_2=#`
and makes `ports-check` probe a host named `127.0.0.1 # …`.

**Reproduction:** `docker compose config` on a file holding the exact template lines:
```
ADMIN_PASSWORD: '# long; the admin login'
MASTER_KEY: '# openssl rand -base64 32 (encrypts keys and tokens at rest)'
SLACK_SIGNING_SECRET: '# Basic Information → App Credentials'
LOG_LEVEL: info            CALCOM_API_KEY: cal_live_...
```
`node --env-file` on the same file: all three empty strings. Makefile with
`APP_BIND_ADDRESSES=127.0.0.1 # added by a user`: `APP_PUBLISH_2=# docker compose … -f compose.publish-2.yml`.

**Proposed fix:** move every comment in `.env.example` onto its own line above the variable and say
"no inline comments" in the header; have `check-ports.mjs` and the Makefile strip ` #…` (`sed
's/[[:space:]]#.*//'`); optionally refuse at boot any value that starts with `#`.

### R2-3 [medium] `slackConnected` never turns false when the socket is lost

**Where:** `src/slack/app.ts:41-49`; `node_modules/@slack/socket-mode/dist/src/SocketModeClient.js:158-171`.

**What:** The status mirrors the client's `connected` and `disconnected` events. With
`autoReconnectEnabled: true` (what the app sets) the socket-mode client, on an unexpected close,
schedules a reconnect and emits only `reconnecting` (after `clientPingTimeoutMS × failures`) and
later `connected`; it emits `disconnected` only for an explicit `disconnect()`. So after a network
outage or a Slack-side `disconnect` frame, `/health` and the Workspaces page keep saying
"connected" until the reconnect succeeds, and never say anything if it keeps failing. The
documented troubleshooting ("`/health` shows `slackConnected: false`") cannot trigger for a
runtime loss, only for a failed boot. `make status` after a restart does flip correctly because
that is a fresh process (observed: false at +1.46 s, true at +1.73 s).

**Reproduction:** code reading; `SocketModeClient.js:166-170`: `if (!this.shuttingDown &&
this.autoReconnectEnabled) { this.delayReconnectAttempt(this.start); } else { this.emit(State.Disconnected); }`.

**Proposed fix:** also listen for `close` and `reconnecting` (set `slackConnected = false`,
record `slackLastDisconnectAt`), keep `connected` → true; show "reconnecting since …" on the
Workspaces page.

### R2-4 [medium] `make manifest` cannot run at the step the guide puts it, and dies with a stack trace

**Where:** `src/cli/manifest.ts:6` (`loadConfig()` with no `ConfigError` handling);
`DEPLOYMENT.md` §1–2 and `README.md` "Setup" (`make manifest` before the Slack app exists);
`src/config/env.ts:20-27` (requires `SLACK_SIGNING_SECRET`, `ADMIN_PASSWORD`, `MASTER_KEY` and, in
multi mode, client id/secret).

**What:** The manifest only needs `OWNER_NAME`, `BOT_NAME`, `INSTALL_MODE` and `PUBLIC_BASE_URL`,
but the CLI loads the full configuration. A colleague following §1–2 literally has no signing
secret yet (it is collected *after* creating the app from the manifest), so the step fails; the
error is the bare Node stack trace of `ConfigError` rather than the one-line message the README
promises for configuration errors. The T8 fresh-clone run passed only because throwaway values
were typed in first; the guide does not say to do that.

**Reproduction:** `node --env-file=.env.example dist/cli/manifest.js` → exit 1, 12 lines of stack,
`ConfigError: Invalid configuration: SLACK_SIGNING_SECRET, ADMIN_PASSWORD, MASTER_KEY. …`.

**Proposed fix:** give the manifest CLI a reduced schema (identity, mode, public URL) or make the
Slack secrets optional for it; catch `ConfigError` in every CLI entry point and print the message
only; in `DEPLOYMENT.md` §1 list the values needed before `make manifest`.

### R2-5 [medium] The install-failure page can never show the codes the troubleshooting table names

**Where:** `src/slack/install-routes.ts:47-52` (prints `error.code ?? error.name`);
`DEPLOYMENT.md` §8 rows "Install page says `invalid_state`" and "Install page says
`bad_client_secret`"; `docs/architecture/slack.md` "Pitfalls".

**What:** `@slack/oauth` surfaces Slack API failures of the code exchange (`bad_client_secret`,
`invalid_code`, `invalid_client_id`, `code_already_used`) as a `WebAPIPlatformError` whose `.code`
is `slack_webapi_platform_error`; the Slack reason is in `error.data.error` and is neither shown
nor logged. The page therefore prints `slack_webapi_platform_error` for a wrong client secret, an
expired code and a replayed callback alike, while telling the operator to look for the string
`bad_client_secret`. The state error is `slack_oauth_invalid_state`, not `invalid_state`.

**Reproduction (scratch, fake client credentials):**
```
callback with cookie+state+fake code      → 400  Slack reported slack_webapi_platform_error
replay of the same callback               → 400  Slack reported slack_webapi_platform_error
callback with state but no cookie         → 400  Slack reported slack_oauth_invalid_state
callback with error=access_denied         → 400  Slack reported slack_oauth_installer_authorization_error
log: {"code":"slack_webapi_platform_error","msg":"slack install failed"}
```

**Proposed fix:** on the failure page and in the log line add `(error as {data?: {error?:
string}}).data?.error` when present; update the two table rows and `slack.md` with the real codes.

### R2-6 [medium] Restore procedure ignores the WAL files; backup doc names the wrong mechanism

**Where:** `DEPLOYMENT.md` §7 ("copy the backup over `calendar-agent.db` inside the `data`
volume"), `docs/architecture/data.md` "Backups" ("`VACUUM INTO`"); `src/db/sqlite.ts:19` (WAL
mode) and `:26-30` (online backup API).

**What:** The live volume holds `calendar-agent.db`, `calendar-agent.db-wal` and
`calendar-agent.db-shm` (observed, owned by `node`). Copying a backup over the main file while a
stale `-wal` remains lets SQLite replay old frames onto the restored file on the next open, which
silently mixes the two states. The backup itself is fine (`node:sqlite` `backup()`, a consistent
snapshot; `make db-backup` copies it out and removes it from the volume), but the doc says
`VACUUM INTO`, which is a different mechanism.

**Reproduction:** `docker exec calendar-agent-app-1 ls -la /data` →
`calendar-agent.db 86016`, `calendar-agent.db-shm 32768`, `calendar-agent.db-wal 0` (sizes vary).

**Proposed fix:** in §7 and `data.md`: "stop the container, delete `calendar-agent.db-wal` and
`calendar-agent.db-shm`, copy the backup over `calendar-agent.db`, start"; correct the mechanism
name; consider a `make db-restore f=…` target that does exactly this.

### R2-7 [low] "Remove" of the home workspace is undone at the next restart

**Where:** `src/slack/authorize.ts:43-54`, `src/db/repos/installations.ts:48-63` (`get` ignores
removed rows; `upsert` sets `removed_at = NULL`); `src/admin/routes/workspaces.ts:19,26`;
`docs/architecture/slack.md` "Removing a workspace".

**What:** While `SLACK_BOT_TOKEN` is in `.env` (single mode always; multi mode optionally), every
boot re-seeds its workspace: a row removed in the admin is resurrected with the env token. If the
env token later belongs to a different team, both rows stay active and the old one keeps a stale
token (events from it produce `invalid_auth` errors in the log, no crash). The single-mode page
says the env token "is the only installation" yet offers a Remove button.

**Reproduction (dist modules, temp DB):** seed → `{seeded:true}`; `remove('T1')` → `true`,
active 0; seed again with the same token → `{seeded:true}`, active 1; seed with a token of team
`T2` → active rows `['T1','T2']`.

**Proposed fix:** document it ("to remove the home workspace, also delete `SLACK_BOT_TOKEN` from
`.env`"), hide Remove for the `installed_by = 'env'` row in single mode, and log a warning when the
env token's team differs from an already stored one.

### R2-8 [low] OAuth routes bypass the security-header hook

**Where:** `src/slack/install-routes.ts:35,40` (`reply.hijack()`), `src/admin/server.ts:43-50`
(`onSend` hook).

**What:** Hijacked replies skip `onSend`, so the install redirect and the success/failure HTML pages
carry no CSP, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` or `Cache-Control`.

**Reproduction:** `GET /slack/oauth_redirect?code=x&state=y` → headers are only `Set-Cookie`,
`content-type`, `Transfer-Encoding`.

**Proposed fix:** set the same headers on `reply.raw` before handing it to `@slack/oauth`, or
render the pages through Fastify and pass only the status/body from the callbacks.

### R2-9 [low] Signal handlers are registered after the network steps

**Where:** `src/index.ts:59-86`; `node_modules/@slack/web-api/dist/WebClient.js:123` (default
retry policy `tenRetriesInAboutThirtyMinutes`); `SocketModeClient.js:289-297` (recoverable
`apps.connections.open` errors retry forever).

**What:** `SIGTERM`/`SIGINT` handlers are attached only after `auth.test` and `app.start()`
resolve. Node is PID 1 in the container (`docker top`: `node dist/index.js`, no `init`), and PID 1
ignores signals it has no handler for, so during a slow boot (Slack unreachable: `auth.test`
retries for up to ~30 minutes, then the socket client loops on recoverable errors) `docker stop`
waits the 10 s grace period and kills the process. With an *invalid* token the boot is fast and
contained (verified). A second signal during shutdown would call `repos.db.close()` twice.

**Reproduction:** code reading; the happy path is fine: live restart logged `shutting down` and the
process exited 0 in 25 ms (scratch) / the container restarted in 0.54 s.

**Proposed fix:** register the handlers right after the HTTP server listens, guard re-entry, and
pass a short `retryConfig` to the seeding `WebClient`.

### R2-10 [low] Sandbox and CLI context defaults differ from Slack's in two small ways

**Where:** `src/admin/routes/sandbox.ts:55` (`… || 'UTC'`), `src/cli/ask.ts:28`
(`DateTime.fromISO(nowRaw, { zone: tz ?? 'UTC' })`), `Makefile:112` (help text for `now=`).

**What:** All three surfaces call the same `AnswerPipeline.ask` with equivalent context
(`userId`, `entryPoint`, `askerTz`, `askerLocale`, optional `now`); parity on the pipeline holds.
Divergences: when no zone is given, the sandbox sends `UTC` whereas Slack sends `null` (→ owner
zone), so the "Slack has no timezone" branch cannot be reproduced from the sandbox; `make ask
now=…` without `tz=` interprets the pretend-now in UTC while the asker zone becomes the owner's,
and the help text does not say which zone `now` is in.

**Reproduction:** sandbox POST without `tz`/`tz_custom` → debug panel `Zone: UTC (asker)`.

**Proposed fix:** sandbox: leave `askerTz` null when both fields are empty (label the option
"(none — owner's zone)"); CLI: interpret `--now` in `--tz` if given, else in the owner's schedule
zone, and say so in `make help`.

### R2-12 [low] Makefile edge cases: `make status` port parsing, own-container detection, three addresses

**Where:** `Makefile:92` (`status`), `scripts/check-ports.mjs:34-40` (`ownContainerHolds`),
`Makefile:8-11` vs `src/config/env.ts:91-92`.

**What:** `make status` builds the URL with `grep … | cut … || echo 8400`; the `||` tests `cut`'s
status, so the fallback never fires, and a quoted `APP_PORT="8400"` yields
`http://127.0.0.1:"8400"/health`. `check-ports.mjs` treats a port as "held by our own container"
only when the container name starts with `calendar-agent`; with any other `COMPOSE_PROJECT_NAME`,
`make up` on an already running stack fails with `FAIL … in-use`. With three addresses the Makefile
silently publishes the first two while the app refuses to start (`APP_BIND_ADDRESSES must list one
or two addresses`) → crash loop under `unless-stopped` and "not healthy yet".

**Reproduction:** `make -n status` with `APP_PORT="8400"` → `curl -sf http://127.0.0.1:"8400"/health`;
`make -n ps` with `127.0.0.1,100.1.2.3,10.0.0.1` → `APP_PUBLISH_2=100.1.2.3`, third dropped.

**Proposed fix:** strip quotes/comments in `status` and use `${APP_PORT:-8400}` from a sourced
value; match the compose project label instead of the name prefix; fail `make up` when more than
two addresses are listed.
