## Findings

### R3-1 [high] The master-key rotation procedure in `release.md` cannot be followed and leaves the instance unhealthy
- Where: `docs/development/release.md` lines 10–12; verified in the clone (phases A3 and C below).
- Claim vs reality: "the master key cannot be rotated in place (re-enter the keys in the admin after changing it)". After changing `MASTER_KEY` every stored ciphertext fails to decrypt (`src/crypto/envelope.ts` throws `DecryptionError`), and nothing catches it: `grep DecryptionError src/` finds no handler outside `src/crypto/`. Consequences, all observed: the Settings page calls `getSecret` to mask the keys (`src/admin/routes/settings.ts:21`) → **500 `{"error":"internal"}`**, so the keys cannot be "re-entered in the admin"; `/health` counts `installations.list()` (`src/admin/server.ts:60`), which decrypts every bot token (`src/db/repos/installations.ts:80`) → with one stored workspace **`/health` is 500**, the compose healthcheck fails (`r.ok` false, exit 1) and the container goes "unhealthy"; `/workspaces` → 500; `src/slack/authorize.ts:10` throws for every Slack event, so the bot answers nothing; `seedInstallationFromToken` calls `repo.get` after `auth.test` and fails too ("SLACK_BOT_TOKEN seeding failed"). The live instance is in exactly the exposed configuration (`installMode: multi`, `workspaces: 1`, two encrypted settings).
- Why it matters: an operator who does what this sentence says ends with a dead bot, a red healthcheck and the two admin pages needed for the recovery returning 500, and no document says how to get out. Rated high rather than critical because the trigger is a deliberate, rare action and putting the previous `MASTER_KEY` back restores everything without data loss (the doc does not say that either).
- Fix (doc, now): replace the sentence with the real procedure: "Rotating `MASTER_KEY` invalidates every stored secret. To rotate: `make db-backup`; `make down`; change `MASTER_KEY`; remove the rows the old key encrypted (`settings` where `encrypted = 1`, every `slack_installations` row); `make up`; paste the Cal.com and DeepSeek keys in Settings; in `multi` mode re-install each workspace (the home workspace is re-seeded from `SLACK_BOT_TOKEN`). To undo, put the previous key back and `make restart`." Fix (code, recommended for R4): `SettingsRepository.getSecret`/`list` and `InstallationsRepository.get`/`list` should treat an undecryptable row as absent and log a warning naming the key id (`ciphertext made with key "k1"`), so `/health`, Settings and Workspaces stay usable and the documented "re-enter" step becomes possible; a boot-time message listing undecryptable rows would make the state visible in `make logs`.

### R3-2 [medium] The template's placeholder keys pass validation, are seeded at first boot, and then shadow every later `.env` edit
- Where: `.env.example` lines 36, 40, 56, 58 (`SLACK_APP_TOKEN=xapp-...`, `SLACK_BOT_TOKEN=xoxb-...`, `CALCOM_API_KEY=cal_live_...`, `DEEPSEEK_API_KEY=sk-...`); `DEPLOYMENT.md` §1 ("For the next step only the identity part is needed"), §6 ("`make restart` after editing `.env`"), §8 (no row); verified in phases A and A2.
- Claim vs reality: `src/config/env.ts:20,22` validate only the prefixes (`/^xapp-/`, `/^xoxb-/`) and `seedSecretsFromEnv` (`src/db/repos/settings.ts:111`) seeds any non-empty value, so a first boot with the template lines untouched logged `"seeded":["calcom_api_key","deepseek_api_key"]` and the decrypted rows were literally the strings `cal_live_...` and `sk-...`; Settings shows `current: ••••_...` and `current: ••••`. After editing `.env` with another value and restarting, the boot log shows `"seeded":[]` and the stored value is unchanged, because the database always wins (`src/services/keys.ts:8`, documented in `data.md`). The only user-visible symptom is "cannot check right now" with `calcom:unauthorized` in the query detail. With Slack on, `xapp-...`/`xoxb-...` also boot "successfully" (health ok) with Slack dead and the reason only in `make logs`.
- Why it matters: `DEPLOYMENT.md` itself encourages filling identity first; a newcomer who starts the instance before holding the provider keys (the scope says the sandbox "works before any Slack app exists") gets a silently broken instance and will edit `.env` and `make restart` in vain, which §6 presents as the way to apply `.env` changes.

Fix (doc): troubleshooting row "Test connection fails and the key shows `••••_...` → the template placeholder was seeded at first boot; paste the real key in Settings (`.env` no longer applies to these two keys)"; in §6 qualify "`make restart` after editing `.env`" with "(except the two provider keys once seeded: rotate them in Settings)".

### R3-3 [medium] `make ask` runs against a second, host-side database, not the instance
- Where: `DEPLOYMENT.md` §5 ("`make ask q=...` # the engine from the command line"), `README.md` §Make commands, `docs/architecture/pipeline.md` ("Slack handlers, the admin sandbox and `make ask` all call it"), Makefile line 108; verified in phase B.
- Claim vs reality: `src/cli/ask.ts:31–32` opens `createRepositories(config.DATA_DIR, …)` with `DATA_DIR` defaulting to `./data` on the host (`src/config/env.ts:31`) and then runs `seedSecretsFromEnv`. The first `make ask` therefore creates `./data/calendar-agent.db` on the host, seeds a **second encrypted copy of the provider keys** there, and logs the question there. Observed: the cli rows appeared in the host database and would never appear in the container's Queries page; a key rotated in the admin is not used by `make ask` (its own first-seeded value wins, `keys.ts:8`); the host copy of the secrets lives outside the volume and outside `make db-backup`.
- Why it matters: the operator is told the CLI is "the engine"; they will look for the row in Queries, or test a rotated key with `make ask` and draw the wrong conclusion.
- Fix: either document it ("`make ask` is a developer tool: it uses `./data` on the host, seeds its own copy of the keys from `.env`, and its questions are not in the admin") or, better, run it in the container: `$(COMPOSE) exec -T app node dist/cli/ask.js …` (then `DATA_DIR` is the volume, the keys are the admin's, the row shows in Queries with entry point `cli`), keeping the host form under another name for development.

### R3-4 [medium] `make -n rebuild` really restarts the stack; `make -n db-shell` really opens sqlite3
- Where: Makefile line 65 (`rebuild: $(MAKE) build && $(COMPOSE) up -d --force-recreate`) and line 103 (`db-shell: @$(MAKE) db-backup >/dev/null && sqlite3 …`).
- Claim vs reality: GNU make executes a recipe line that contains `$(MAKE)` even under `-n` (manual, "Instead of Executing Recipes"): the sub-make only prints, but the rest of the shell line runs. Proven twice: a synthetic Makefile with the same shape (`make -n rebuild` created the `SIDE_EFFECT` file), and the clone with `COMPOSE='echo [COMPOSE-RAN]'`, whose output ends with `[COMPOSE-RAN] up -d --force-recreate` printed by an echo that executed. In the project directory `make -n rebuild` would have recreated the live container, which is why it was not run there.
- Why it matters: `make -n` is the normal way to preview a target before running it on a production host; previewing `rebuild` restarts production (and recompiles nothing on the host, see R3-25).
- Fix (Makefile): express the chains as prerequisites instead of inline `$(MAKE)`: `rebuild: build` with the recipe `$(COMPOSE) up -d --force-recreate`; `db-shell: db-backup` with the recipe `sqlite3 $$(ls -t backups/*.db | head -1)`. `tests/repo/scripts-and-cli.test.ts` already dry-runs `status` and `up`; add `rebuild` with a stub `COMPOSE` and assert nothing beyond printing happens.
